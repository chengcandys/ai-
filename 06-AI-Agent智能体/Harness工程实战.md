# 深入专题 · Harness 工程实战（六层框架 + 成熟度阶梯 + 一线案例）

> "The model is the agent. The code is the harness. Build great harnesses. The agent will do the rest."
> Harness = 模型之外的一切：系统提示、工具、文件系统、沙箱、编排、钩子、反馈回路、约束。

## 1. 为什么模型做不到，必须 Harness 补

| 模型做不到的事 | Harness 怎么补 | 组件 |
|----------------|----------------|------|
| 记住多轮历史 | 维护对话历史逐轮拼入 | 记忆系统 |
| 执行代码/命令 | 提供 Bash 与代码执行环境 | 通用执行环境 |
| 获取实时信息 | 接入搜索、MCP 工具 | 外部知识获取 |
| 操作文件环境 | 抽象文件系统 + Git 版本控制 | 文件系统 |
| 判断自己做对没 | 沙箱、测试、浏览器自动化 | **验证闭环** |
| 长任务保持连贯 | 压缩、记忆文件、进度追踪 | 上下文管理 |

## 2. 六层检查框架（Harness 自查清单）

| 层 | 名称 | 解决什么 | 关键设计 |
|----|------|----------|----------|
| L1 | **信息边界层** | Agent 该知道/不该知道什么 | 角色与目标定义、无关信息裁剪、任务状态结构化 |
| L2 | **工具系统层** | 怎么与外部世界交互 | 工具选型、调用时机控制、结果提炼反馈 |
| L3 | **执行编排层** | 多步骤任务怎么串 | "理解目标→判断信息→分析→生成→检查"的轨道 |
| L4 | **记忆与状态层** | 中间结果怎么管 | 任务状态、中间产物、长期记忆独立管理 |
| L5 | **评估与观测层** | 怎么知道做对了没 | **独立于生成过程的验证机制** |
| L6 | **约束校验与恢复层** | 出错了怎么办 | 预设规则拦截、重试/回滚/降级 |

**类比新员工入职**：L1 岗位说明、L2 办公工具、L3 标准操作流程、L4 项目管理系统、L5 质检流程、L6 红线规则与应急预案。

**起步建议**：不要六层一起建。**先补 L1（任务边界）和 L6（拦截与恢复）**——投入最小、防呆收益最大；再按需补编排、状态与观测。

## 3. 上下文管理：Harness 的第一痛点

详见 [上下文工程详解](./上下文工程详解.md)。Harness 层面的三个动作：

1. **监控**：上下文利用率纳入可观测（Dex Horthy 观察：168K 窗口过 ~40% 质量下滑，即 Smart/Dumb Zone，阈值需自测）
2. **交接**：context resets —— 清空上下文 + 结构化交接文档（目标/进度/失败原因/验证命令/文件清单）
3. **渐进披露**：AGENTS.md 只当目录（~100 行），细则放子文档按需加载（OpenAI 实践）

## 4. 工程实践优先级（P0 → P2）

### P0：今天就能做
| 行动 | 参考实践 |
|------|----------|
| 维护 `AGENTS.md` | Hashimoto：每一行对应一个历史失败案例，持续积累成防错系统 |
| 自定义 Linter + 修复指令 | OpenAI：报错信息自带修复方法（错误即上下文） |
| 团队知识入仓库 | OpenAI：仓库是唯一事实来源（Slack/Wiki 对 Agent 不稳定可见） |

⚠️ AGENTS.md 别写成超级 System Prompt——当目录用，详细规则子文档化按需加载。

### P1：P0 稳定后
- 分层上下文管理（渐进披露）、进度文件（JSON 结构化追踪任务列表）
- 端到端验证能力（Playwright/Puppeteer MCP，让 Agent 亲眼看到运行结果）
- 上下文利用率控制与压缩触发

### P2：规模化后
- Agent 专业化分工（去重/优化/文档专职 Agent）
- 定期"垃圾回收"（OpenAI：后台清理 Agent 对抗代码库熵增）
- 深度可观测（把 Chrome DevTools 等暴露给 Agent）

## 5. Harness 成熟度阶梯（你在哪一级？）

| 级别 | 特征 | 工程师角色 |
|------|------|-----------|
| L0 无 Harness | 直接给 Prompt | 手写代码 |
| L1 基础约束 | AGENTS.md、Linter、手动测试 | AI 辅助 |
| L2 反馈回路 | CI/CD 集成、自动化测试、进度追踪 | 规划与审查 |
| L3 专业化 Agent | 多 Agent 分工、分层上下文、持久记忆 | 设计环境、管理执行 |
| L4 自治循环 | 无人值守并行、自动清理、自修复 | 架构设计、质量把关 |

## 6. 一线案例拆解

### OpenAI（3 人 5 个月 100 万行代码，0 行手写，~1500 PR）
- 目录式 AGENTS.md + **机械化执行架构约束**（"If it cannot be enforced mechanically, agents will deviate"——能写进 linter 的规则绝不写进文档）
- 可观测性暴露给 Agent 自己看；后台清理 Agent 对抗熵增

### Anthropic
- Carlini：16 个并行 Agent（~2000 会话）写出通过率 99% 的 C 编译器；日志写文件且 grep 友好、测试子采样、独立去重 Agent
- 借鉴 GAN 的三智能体：Planner → Generator ⇄ Evaluator，解决上下文焦虑与"自己评自己"的偏差
- **关键教训**：Sonnet 4.5 → Opus 4.6 后 Sprint 机制可以移除——**Harness 组件编码的是对模型能力的假设，模型升级后要定期重新验证并裁剪**

### Stripe Minions（每周 1300+ 无人值守 PR）
- Devbox 预热池、混合编排状态机（确定性节点 + Agent 节点）
- Toolshed MCP 近 500 工具**按子集分发**（工具治理的范本）
- 秒级 lint + 最多 2 轮 CI（two-strike 后升级人工）
- 理念："**What's good for humans is good for agents**"——为人造的好环境（快速反馈、清晰文档）对 Agent 同样好

### Thoughtworks（Böckeler）三类归纳
Context Engineering / Architectural Constraints / Garbage Collection；并指出两大空白：**棕地改造**与**AI 生成代码的独立验证**（"用 AI 写的测试验证 AI 写的代码，像用同一双眼睛检查自己的作业"）。

## 7. 开放问题（面试谈认知用）

1. 棕地（存量代码库）改造方法不成熟
2. 功能正确性的独立验证薄弱
3. AI 代码的长期可维护性未知
4. Harness 做厚还是做薄？——场景决定；模型变强后应定期简化
5. 单 Agent 还是多 Agent？——规模决定；先榨干单 Agent

## 8. 落地最短路径

```
入口约束（AGENTS.md + Linter）→ 自动验证（编译/测试跑给 Agent 看）
→ 失败反馈为可执行操作（报错带修复指令）→ 观测（Trace）→ 再谈编排与自治
```

一句话：**从最短闭环开始，让验证结果而不是人的感觉来驱动 Agent 迭代。**

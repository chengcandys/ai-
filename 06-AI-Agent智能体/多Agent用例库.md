# 用例库 · 多 Agent 协作（15 个行业场景）

> 架构原理见 [多Agent协作详解](./多Agent协作详解.md)。每个用例给出：**场景 → 架构 → 关键设计 → 教训**。可按需套用到自己的业务。

## 一、软件研发

### 用例 1：并行功能开发（前端 + 后端 + 测试）
- **场景**：一个需求同时涉及 API、UI、测试，串行开发慢
- **架构**：主从编排——Lead 拆接口契约 → 前端 Agent / 后端 Agent 并行 → 测试 Agent 独立验证
- **关键设计**：先由 Lead 产出**接口契约（Spec）**再并行，否则合并时对不上
- **教训**：无契约的并行 = 更高的返工成本；契约就是"上下文隔离"的边界

### 用例 2：大型代码库现代化迁移
- **场景**：10 万行代码从 Java 8 升到 Java 21，人工需数月
- **架构**：主从 + 流水线——分模块并行迁移 Agent + 每模块独立验证 Agent + 专职去重 Agent
- **关键设计**：日志写文件且 grep 友好（Agent 可自查）；测试子采样控成本；专职 Agent 去重
- **教训**：并行 Agent 会重复造轮子，**去重 Agent 是必需而非可选**（Anthropic 实证）

### 用例 3：代码评审委员会（多视角评审）
- **场景**：单人评审易漏（安全、性能、可读性关注点不同）
- **架构**：辩论/投票——安全 Agent、性能 Agent、可维护性 Agent 各自评 → 汇总 Agent 合并去重 + 冲突仲裁
- **关键设计**：每个 Agent 有专属检查清单；冲突时以规则优先级裁决而非平均
- **教训**：多视角的价值在于"关注点隔离"，同一 prompt 换个说法不叫多视角

### 用例 4：遗留系统文档重建
- **场景**：无文档的老系统需补充架构文档
- **架构**：流水线——扫描 Agent（列模块）→ 分析 Agent（读代码提炼职责）→ 撰写 Agent（成文）→ 校验 Agent（对照代码核查）
- **关键设计**：撰写与校验必须不同 Agent（自己查自己等于没查）
- **教训**：生成与验证分离是多 Agent 最被低估的价值

## 二、内容与研究

### 用例 5：深度研究系统（Deep Research）
- **场景**：一份行业研究报告需查 100+ 来源
- **架构**：主从——Lead 规划子问题 → 3~5 个检索 Agent 并行 → 汇总 Agent 综合 → 引用校验 Agent 核对
- **关键设计**：子 Agent 只回传"结论 + 来源链接"，不回传原始网页（省主上下文）
- **教训**：token 消耗约为单 Agent 15 倍 → 只用于高价值任务

### 用例 6：多平台内容工厂
- **场景**：一个主题要产出公众号长文、小红书笔记、短视频脚本
- **架构**：流水线——素材 Agent（调研）→ 长文 Agent → 改写 Agent（各平台风格）+ 配图 Agent（文生图）+ 审核 Agent
- **关键设计**：风格规范做成 Skill 按需加载，而非塞进每个 Agent 的 prompt
- **教训**：平台化改写用"同一个事实 + 不同风格模板"，避免事实各写各的导致互相矛盾

### 用例 7：事实核查流水线
- **场景**：AI 生成内容上线前需核查事实
- **架构**：流水线——断言抽取 Agent（拆句子）→ 检索 Agent（找证据）→ 判定 Agent（支持/反驳/无据）→ 汇总 Agent
- **关键设计**：判定 Agent 只看"断言 + 证据"，不看原稿（防被原稿语气带偏）
- **教训**：把"抽取"和"判定"分离，准确率显著高于"一次问模型对不对"

### 用例 8：本地化翻译协作
- **场景**：产品文档译成 8 种语言且术语统一
- **架构**：主从——术语库 Agent 先行 → 各语种翻译 Agent 并行 → 术语一致性 Agent 终检
- **关键设计**：术语表作为共享工件（artifact）而非靠 prompt 传递
- **教训**：共享状态用文件而非对话历史，避免多 Agent 上下文各存一份漂移

## 三、企业与运营

### 用例 9：客服工单智能分派
- **场景**：日 5000 工单，人工分类慢且错分率高
- **架构**：路由 + 专业 Agent——意图识别 Agent → 售后/账单/技术专家 Agent → 升级 Agent（判断转人工）
- **关键设计**：每个专家 Agent 工具集聚焦（只给它需要的查询工具）
- **教训**：专家 Agent 的收益来自"工具与知识的聚焦"，不是"人格设定"

### 用例 10：财务对账与异常排查
- **场景**：月度对账差异需人工逐笔排查
- **架构**：流水线——数据勘探 Agent（定位差异批次）→ 假设生成 Agent（列可能原因）→ 验证 Agent（跑规则/SQL 验证）→ 报告 Agent
- **关键设计**：任何写操作（调账）走人工审批，Agent 只做诊断
- **教训**：高风险领域"多 Agent 只读诊断 + 人审批执行"是安全边界

### 用例 11：招聘简历初筛
- **场景**：单岗位 2000 份简历
- **架构**：流水线——解析 Agent（结构化简历）→ 匹配 Agent（对照 JD 打分+理由）→ 偏见检查 Agent（检测歧视性筛除）→ 人工复核
- **关键设计**：必须留"打分的理由"以便人工快速复核与申诉
- **教训**：涉及人的决策必须有可解释性 + 人工终审（合规红线）

### 用例 12：市场竞品监控（Loop + 多 Agent）
- **场景**：每周跟踪竞品动态并出简报
- **架构**：Loop 触发（定时）→ 采集 Agent（多源抓取）→ 分析 Agent（分类+影响判断）→ 撰写 Agent → 推送
- **关键设计**：跨会话状态用文件持久化（上次已报告的内容不重复）；异常时升级人工
- **教训**：Loop 工程的瓶颈不是循环，而是**状态持久化与去重**

## 四、专业技术领域

### 用例 13：医疗影像辅助诊断（人机协作式多 Agent）
- **场景**：影像初筛，医生复核
- **架构**：流水线——质控 Agent（图像质量）→ 检测 Agent（标注可疑区域）→ 检索 Agent（匹配相似历史病例）→ 报告草稿 Agent → 医生终审
- **关键设计**：每个结论必须给"依据 + 置信度"，输出面向医生而非患者
- **教训**：医疗场景 Agent 的定位是"减少医生重复劳动"，不是替代判断

### 用例 14：法律合同审查
- **场景**：批量合同需查风险条款
- **架构**：流水线——条款切分 Agent → 风险识别 Agent（对照风险库）→ 生成-评审循环（改写建议 + 评审 Agent 复核）→ 律师终审
- **关键设计**：风险等级分级（高/中/提示），高风险必须人审
- **教训**：生成-评审（Generator-Critic）模式在"质量优先"任务上收益最大

### 用例 15：运维故障根因分析（RCA）
- **场景**：线上故障，需快速定位根因
- **架构**：黑板共享状态——多 Agent 并行查不同维度（日志/指标/变更/依赖），实时写入共享黑板，诊断 Agent 汇总收敛
- **关键设计**：共享结构化状态（时间线 + 假设 + 证据），而非各自对话
- **教训**：黑板模式适合"需要持续共享中间结论"的并发排查；写操作修复仍需人工审批

## 通用经验（15 个用例的共性提炼）

1. **拆分靠"关注点隔离"**：安全/性能/事实/风格各一 Agent，而非按"角色名称"
2. **生成必须与验证分离**：自己查自己等于没查（用例 4/7/12 反复验证）
3. **共享状态用工件（文件/结构化 State）**：不用对话历史传递，防漂移
4. **去重与仲裁是必需组件**：并行越多越需要（用例 2/3/5）
5. **写操作/不可逆动作留给人**：Agent 负责诊断与建议，人负责执行（用例 10/13/14/15）
6. **先算账再上多 Agent**：4~15 倍 token 成本，只在高价值任务上划得来

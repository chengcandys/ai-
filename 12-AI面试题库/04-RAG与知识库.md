# 04 · RAG 与知识库（25 题）

## 基础原理

### Q1. 什么是 RAG？解决什么问题？
- 检索增强生成：先从知识库检索相关内容，再把"问题+检索结果"交给 LLM 生成
- 解决三大痛点：知识截止、私有数据不可用、幻觉（可附引用来源）
- 本质：把 LLM 从"闭卷考试"变成"开卷考试"

### Q2. RAG 完整链路有哪些环节？
```
文档解析 → 切分(Chunking) → Embedding → 向量入库
                                        ↓
用户问题 → 查询改写 → 检索(召回Top-K) → Rerank → 拼装Prompt → LLM生成 → 引用溯源
```
- 面试金句：**RAG 的效果是级联的，每个环节的误差会逐级放大**（文档预处理 × 召回质量 × 生成忠实度）

### Q3. RAG 落地最难的地方在哪？（高频）
1. **文档预处理**：PDF 表格/图片/多栏排版解析差，垃圾进垃圾出
2. **召回质量**：切分不合理、查询与文档表达不匹配 → 该捞的捞不到
3. **生成忠实度**：检索到了但模型不照着答（仍幻觉）
- 答题结构：按三环节展开 + 各自优化手段 + 如何定位瓶颈（评测）

## 切分与索引

### Q4. Chunk 切分策略有哪些？怎么选？
- 固定长度（简单但切断语义）、按结构（标题/段落/句子）、语义切分、滑动窗口重叠（10~20%）
- 经验值：中文 300~500 字/块，配合重叠；按文档类型调（法律条款按条、代码按函数）
- 原则：一个 chunk 应包含一个完整语义单元

### Q5. Chunk 太大/太小各有什么问题？
- 太大：噪声稀释关键信息、占用上下文、embedding 语义模糊
- 太小：语义不完整、上下文断裂、召回数量需求变大
- 加分：父子索引（小块用于检索命中，返回其所属大块给 LLM）

### Q6. Embedding 模型怎么选？
- 维度与效果权衡（512~3072 维）
- 中文场景选中文优化的模型（BGE、M3E、GTE 系列）；多语言选 multilingual
- 领域适配：通用模型在垂直领域（医疗/法律）效果差 → 可用领域语料微调 embedding
- 评估：MTEB/C-MTEB 榜单 + 自建召回测试集

### Q7. 向量数据库怎么选型？
- 原型/单机：FAISS、Chroma
- 生产/大规模：Milvus、Qdrant、Elasticsearch（支持混合检索）
- 已有 PG 栈：pgvector，减少组件
- 关注点：QPS、召回延迟、过滤检索（metadata filter）、运维成本

### Q8. 相似度度量方式？为什么常用余弦？
- 余弦相似度：只关注方向，不受向量模长影响 → 适合语义比较
- 点积：模长含信息时用；欧氏距离：几何距离
- 注意：embedding 归一化后余弦 ≡ 点积

## 检索优化

### Q9. 什么是混合检索（Hybrid Search）？为什么必须上？
- 向量检索（语义）+ BM25 关键词检索（精确匹配），加权融合（RRF 倒数排名融合）
- 向量短板：专有名词、型号、代码符号召回差；BM25 短板：同义改写召回差 → 互补

### Q10. Rerank 的作用与做法？
- 初检宽松召回 Top-50（快）→ 交叉编码器（Cross-Encoder）精细重排取 Top-5（准）
- 原因：双塔 embedding 检索快但交互浅；Cross-Encoder 把 query+doc 一起编码，判断准但慢 → 两阶段各取所长
- 常用模型：BGE-Reranker、Cohere Rerank

### Q11. 查询改写（Query Rewriting）有哪些手段？
- 指代消解：多轮对话中"它怎么样"→ 补全为完整问题
- 查询扩展：生成同义改写多个 query 并行检索（Multi-Query）
- HyDE：先让 LLM 生成假设答案，用假设答案去检索（答案与文档同分布，召回更好）
- Step-back：把具体问题抽象成上位问题先检索背景

### Q12. 召回率低怎么排查？（实战高频）
1. 构造"问题 → 标准答案所在文档"评测集
2. 单独测召回（答案块是否在 Top-K）与生成（召回对了答得对不对）
3. 召回差 → 查切分/embedding/查询改写；生成差 → 查 prompt/模型能力
- 金句：**先分环节归因，再针对性优化，不要一上来就换模型**

### Q13. 多轮对话的 RAG 怎么做？
- 上下文改写：把历史对话压缩进当前 query 再检索
- 历史也入库：会话摘要存入记忆库，可检索历史结论
- 注意窗口成本：历史 + 检索结果 + 回答要统筹 token 预算

### Q14. 结构化数据（表格/数据库）怎么做 RAG？
- Text-to-SQL：LLM 把问题转 SQL 查数据库（schema 注入 prompt + 执行结果回填）
- 表格：转 Markdown/按行序列化入库，或混合"向量库 + SQL 引擎"双路
- 追问：Text-to-SQL 的准确率如何保障（few-shot 示例、SQL 校验、执行错误自我修正）

## 生成与幻觉治理

### Q15. RAG 场景如何减少幻觉？
- Prompt 层：明确"仅根据给定资料回答，资料不足就说不知道"
- 检索层：提高召回与 rerank 质量（答案根本不在上下文里，模型只能编）
- 生成层：要求逐句引用来源编号，低温度解码
- 校验层：NLI 忠实度检测 / 二次让 LLM 核对答案与来源一致性，不通过则重答或拒答

### Q16. 检索结果与问题不相关时怎么办？
- 设置相关性阈值：rerank 分数过低 → 走拒答/联网搜索兜底
- 让模型自评检索结果是否足以回答（Self-RAG 思路）

### Q17. Self-RAG 是什么？
- 模型在生成中自主决定：是否需要检索、检索内容是否相关、生成是否忠实
- 通过特殊反思 token 训练 → 按需检索，减少不必要的检索开销

### Q18. GraphRAG 是什么？解决传统 RAG 什么短板？
- 传统 RAG 短板：只能捞"局部片段"，回答不了**跨文档全局性问题**（"整个语料库主要讲了哪些主题"）
- GraphRAG：抽取实体关系建知识图谱 → 社区聚类 → 预生成社区摘要 → 全局问题查摘要，具体问题走向量
- 代价：建图成本高（大量 LLM 调用）；LightRAG 等轻量方案做权衡

### Q19. 如何评估一个 RAG 系统？
- 检索侧：Hit Rate、MRR、Recall@K
- 生成侧：忠实度 Faithfulness（答案是否源于检索内容）、答案相关性 Answer Relevancy
- 框架：RAGAS、TruLens；必须有**业务自建评测集**（榜单代替不了真实分布）

### Q20. 知识库文档更新怎么做？
- 增量更新：文档级版本管理，变化文档重新切分+入库，旧向量删除
- 全量重建成本高 → 按更新频率分层（热数据实时、冷数据定时）
- 注意 embedding 模型升级需要全量重建（向量空间不兼容）

## 前沿与权衡

### Q21. Agentic RAG 是什么？
- 把 RAG 从"固定流水线"变成"Agent 自主决策"：是否检索、检索哪个库、检索几轮、结果够不够用
- 代表模式：路由（多知识库选路）、反思重试、规划式多步检索（如先查背景再查细节）

### Q22. 上下文里多个检索块怎么排序？
- 重要内容放**开头和结尾**（Lost in the Middle：模型对中段注意力最弱）
- 按相关性排序 + 去重 + 压缩无关句

### Q23. 上下文压缩怎么做？
- 抽取式：从召回块中抽取与问题相关的句子（LLMLingua 等）
- 摘要式：长文档先摘要再注入
- 目的：省 token、提信噪比，往往同时提升准确率

### Q24. 长上下文模型普及后，RAG 还需要吗？（开放高频题）
- 需要，原因：① 成本——塞 100 万 token 比检索 5 个块贵几个数量级；② 延迟；③ Lost in the Middle 导致长上下文利用率不高；④ 权限控制（不同用户可见不同文档，RAG 天然支持过滤）
- 趋势：长上下文 + RAG 互补——RAG 粗筛、长上下文细读更多候选
- 答题要点：**不要二极管，讲清楚 trade-off**

### Q25. 设计一个企业知识库问答系统，你会怎么设计？（系统设计题）
- 分层作答：
  1. **数据层**：文档接入（解析/清洗）、切分策略、增量更新机制
  2. **检索层**：混合检索 + Rerank + 权限过滤（metadata）
  3. **生成层**：prompt 模板、引用溯源、拒答策略
  4. **评估层**：自建评测集、线上反馈闭环（点踩/点赞回流）
  5. **工程层**：缓存（高频问题命中缓存）、异步索引、可观测（检索日志）
- 加分：主动提冷启动（先小范围试点收集 badcase）、成本估算

## 2026 新增真题（联网补充）

### Q26. ANN 索引怎么选？HNSW / IVF / PQ 对比？
- **HNSW**：分层小世界图，跳表式逼近 → 召回率 95%+、延迟最低、内存最大；核心参数 M（每点边数）、ef_search；Milvus 默认
- **IVF**：先聚类 nlist 个簇，查询只搜 nprobe 个簇 → 内存省，召回与速度靠 nprobe 调
- **PQ**：向量分段量化压缩 8~32 倍 → 亿级必配，精度有损，常与 IVF 组合（IVF-PQ）
- 选型：千万级以下 HNSW；亿级 IVF-PQ + GPU 索引 + 分片

### Q27. 混合检索的融合策略？为什么生产推荐 RRF？
- 手动加权（向量 0.7 + BM25 0.3）：需在验证集上调，且不同 query 最佳权重差异大
- **RRF**：score = Σ 1/(k + rank)，k≈60；只用排名不用分数 → 免疫两路量纲差异，更稳健 → 生产首选

### Q28. RAG 端到端延迟怎么优化？
- 检索侧：HNSW 参数调优（向量检索压到 50ms 内）、元数据过滤前置
- 生成侧：vLLM 部署 + Continuous Batching、KV Cache/Prefix Cache 复用、流式输出（TTFT 先行）、Prompt 压缩
- 链路侧：检索与 LLM 流水线并行、高频问题 Redis 缓存

### Q29. 文档更新后索引怎么更新？
- 全量重建：简单，适合日级低频更新
- 增量更新：变更文档重新切分+embedding，旧向量删除 → 主流
- 双写切换：新索引建好再切流量，零停机 → 大版本/embedding 模型升级时用
- 注意：embedding 模型升级 = 向量空间变化，必须全量重建

### Q30. Bi-Encoder 和 Cross-Encoder 的本质区别？
- Bi-Encoder（检索用）：query/doc 分别编码成向量再算相似度 → 可离线预计算、毫秒级、但两文本无交互，判断粗
- Cross-Encoder（Rerank 用）：query+doc 拼接进同一模型，token 级交互 → 准但慢、不可预计算，只能处理少量候选
- 这就是"粗排 Top-20 → 精排 Top-5"两阶段架构的根本原因

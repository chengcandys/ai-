# 06 · 推理部署与工程落地（20 题）

## 推理优化

### Q1. 大模型推理慢/贵的根源是什么？
- 自回归逐 token 生成：N 个 token 要 N 次前向计算，无法并行
- 内存带宽瓶颈：每步都要把全部权重从显存搬入计算单元（decode 阶段是 memory-bound）
- KV Cache 随序列与并发线性增长，挤占显存限制吞吐

### Q2. Prefill 和 Decode 阶段的差异？
- Prefill（处理输入 prompt）：并行计算全部输入 token → 计算密集（compute-bound）
- Decode（逐个生成）：每步只算 1 个 token → 显存带宽密集（memory-bound）
- 优化策略不同：Prefill 拼算力，Decode 拼带宽 → 分离式部署（PD 分离）成为趋势

### Q3. 模型量化（Quantization）有哪些方式？
- PTQ（训练后量化）：直接量化，简单快速（GPTQ、AWQ）；QAT（量化感知训练）：效果好但成本高
- 精度档位：FP16 → INT8（几乎无损）→ INT4（轻微损失，显存减半以上）
- W4A16：权重 4bit、激活 16bit → 推理显存大降、精度保持好，部署主流

### Q4. vLLM 为什么快？PagedAttention 原理？
- KV Cache 显存管理借鉴操作系统虚拟内存分页：按块（page）分配，避免预分配连续显存造成的碎片与浪费
- 效果：显存利用率大幅提升 → 同卡可服务更多并发 → 吞吐数倍提升
- 配套：Continuous Batching（连续批处理，请求随到随插，不等整批结束）

### Q5. 提升推理吞吐的手段有哪些？
- Continuous Batching、PagedAttention、KV Cache 量化/压缩
- 投机采样（Speculative Decoding）：小模型草拟多 token，大模型一次验证 → 加速 2~3 倍
- 多卡并行：TP（张量并行）/ PP（流水线并行）
- 前缀缓存（Prefix Caching）：相同 system prompt 的 KV 复用

### Q6. 投机采样（Speculative Decoding）原理？
- 小草稿模型快速生成 k 个候选 token → 大模型一次前向并行验证 → 接受最长正确前缀
- 数学上保证输出分布与大模型一致（无损加速）
- 变体：Medusa（模型自身加多个预测头）、EAGLE

### Q7. 首 token 延迟（TTFT）和每 token 延迟（TPOT）分别优化什么？
- TTFT：Prefill 速度 → 影响"多久开始说话" → 优化：prefix cache、prompt 压缩
- TPOT：Decode 速度 → 影响"打字流畅度" → 优化：量化、投机采样、带宽
- 产品体感：TTFT < 1s 是基本要求

### Q8. 端侧（手机/边缘）部署的难点与手段？
- 难点：算力弱、内存小、功耗限制
- 手段：小模型（1~7B）+ 激进量化（INT4 甚至更低）、蒸馏、NPU 适配、MNN/llama.cpp 等端侧框架
- 趋势：端云协同（隐私/简单任务在端，复杂任务上云）

## 训练工程（算法岗）

### Q9. 分布式训练并行策略有哪些？
- **DP 数据并行**：每卡完整模型，切数据 → 简单但模型放不下就不行
- **TP 张量并行**：单层参数切到多卡 → 通信频繁，适合机内
- **PP 流水线并行**：按层切分 → 有气泡需微批次填充
- **ZeRO（DeepSpeed）**：把优化器状态/梯度/参数分片到各卡，按需聚合 → 显存大降
- FSDP（PyTorch 原生 ZeRO 等价物）

### Q10. 混合精度训练怎么做？
- FP16/BF16 计算 + FP32 主权重和优化器状态
- Loss Scaling 防 FP16 梯度下溢；BF16 范围大不易溢出，大模型主流
- 收益：显存减半、吞吐翻倍（Tensor Core）

### Q11. 训练 loss 突然飙升（spike）怎么排查？
- 数据：该批次脏数据/异常长样本
- 学习率过大、梯度爆炸（看 grad norm 监控）
- 硬件：GPU 故障（静默数据损坏）
- 对策：梯度裁剪、降低 lr、跳过坏 batch、checkpoint 回滚续训

### Q12. RLHF/PPO 训练为什么不稳定？
- 两个模型（策略+奖励）+ 采样循环，链路长
- 奖励黑客、KL 散度失控、采样分布漂移
- 对策：严格 KL 控制、reward 归一化、小步长更新 → 这也是 DPO/GRPO 流行的原因

## 应用工程与系统设计

### Q13. 设计一个高并发 LLM API 网关，关键点？
- 请求队列 + 优先级调度、负载均衡（按 GPU 显存/队列长度）
- 流式输出（SSE）、超时与取消、重试与降级（主模型挂→备用模型）
- 限流（按租户 token 配额）、缓存（相同 prompt 命中）、全链路监控

### Q14. 如何降低线上 LLM 应用成本？（高频实战题）
- 模型路由：简单请求给小模型，按复杂度分级
- Prompt 瘦身：压缩 system prompt、少发无关历史
- 缓存：语义缓存（相似问题返回缓存答案）、prefix caching
- 批处理：非实时任务走离线批量 API（通常半价）
- 量化与自部署：量大时自托管开源模型可能更便宜

### Q15. 线上幻觉率怎么监控？
- 抽样人工评审 + LLM-as-Judge 自动评分（忠实度/正确性）
- 用户反馈信号（点踩、追问"你确定吗"）回流
- 关键指标看板 + 版本对比（prompt/模型改动前后回归测试）

### Q16. Prompt 上线如何管理？
- 版本化（git 管理 + 变更评审）、灰度发布（A/B 对比）
- 回归评测集：每次改动跑一遍核心 case 防劣化
- 提示词与代码同等对待：CI/CD 流程

### Q17. 数据安全与合规怎么做？
- 敏感数据脱敏后再出域、私有化部署或专属实例
- 审计日志（谁问了什么）、防 prompt 注入泄露系统提示词
- 国内合规：生成式 AI 备案、内容安全过滤（输入输出双向）

### Q18. 设计一个智能客服系统（综合设计题）
- 路由层：意图识别 → FAQ 直答 / RAG 知识库 / 人工转接
- 知识层：混合检索 + Rerank + 答案引用
- 护栏：拒答范围外问题、敏感词过滤、转人工策略（低置信/用户情绪）
- 闭环：未解决问题回流补充知识库、会话质检
- 指标：解决率、转人工率、平均轮次、满意度

### Q19. 微调和 RAG 并用的场景怎么设计？
- 微调教"行为模式"（输出格式、领域话术、工具调用习惯）
- RAG 供"动态知识"（产品信息、政策条款）
- 分工原则：**知识归 RAG，能力归微调**

### Q20. 如何跟进快速迭代的模型版本升级？
- 评测集先行：自建业务评测集，新模型先跑分再切流
- 抽象模型层：业务代码不绑定具体模型（统一接口/网关）
- 灰度切流 + 快速回滚；成本-效果曲线定期重估（新模型可能让小模型也能胜任原任务）

# 02 · 方案与工具对比（决策表）

## 1. 三大"注入能力"方案对比（最高频选型题）

| 维度 | Prompt 工程 | RAG | 微调（SFT/LoRA） |
|------|-------------|-----|------------------|
| 解决什么 | 说清楚 | 给知识（动态） | 改行为（固化能力） |
| 成本 | 极低 | 中（建库+检索成本） | 中高（数据+算力） |
| 生效速度 | 立即 | 立即（更新文档即生效） | 需训练迭代 |
| 知识更新 | 不支持 | **最佳** | 差（需重训，易幻觉） |
| 可溯源 | 无 | **有（可引用来源）** | 无 |
| 风格/格式一致性 | 差（不稳） | 一般 | **最佳** |
| 延迟 | 低 | 中（+检索） | 低（可合并权重） |
| **结论** | 永远第一步 | 知识类需求首选 | 行为/风格类需求 |

**决策口诀**：能 Prompt 不 RAG，能 RAG 不微调；知识归 RAG，能力归微调。

## 2. RAG vs 长上下文（2024 年后的高频争议）

| 维度 | RAG | 长上下文（塞全量） |
|------|-----|---------------------|
| 成本 | 低（只塞 Top-K） | **极高（每轮全量 token）** |
| 延迟 | 中（+检索） | 高（Prefill O(L²)） |
| 召回精度 | 依赖检索质量（可能漏） | 全量在上下文（不漏，但利用率低） |
| 权限控制 | **天然支持过滤** | 难（要么全给要么不给） |
| 长文利用率 | - | 差（Lost in the Middle） |
| 跨文档全局问题 | 差（需 GraphRAG） | 中 |
| **结论** | 生产默认 | 一次性分析超长文档时用；**主流是"RAG 粗筛 + 长上下文细读"混合** |

**反思**：不要陷入"谁取代谁"的二极管思维——所有技术对比题的满分答法都是**讲清 trade-off + 给组合方案**。

## 3. Workflow vs Agent

| 维度 | Workflow | Agent |
|------|----------|-------|
| 控制权 | 代码（流程写死） | **LLM（自主决策）** |
| token 成本 | 基准 | **4~8 倍** |
| 可预测性 | 高（易测试/调试） | 低（有漂移风险） |
| 适用 | 步骤可枚举的固定流程 | 开放目标、需动态决策 |
| **结论** | 生产保底骨架 | 处理开放分支与异常；**混合架构最优** |

## 4. 单 Agent vs 多 Agent

| 维度 | 单 Agent | 多 Agent |
|------|----------|----------|
| 上下文 | 单一，易被污染 | **隔离（核心收益）** |
| 并行 | 无 | 有（墙钟时间↓） |
| token 成本 | 基准 | **4~15 倍** |
| 调试难度 | 低 | 高（需 trace 汇总） |
| **结论** | **默认先单体榨干** | 仅当"上下文隔离/并行/专业分工"至少占一条才拆 |

## 5. 检索方案对比

| 方案 | 召回（语义/精确） | 速度 | 成本 | 适用 |
|------|-------------------|------|------|------|
| 纯向量 | 语义好 / 精确差 | 快 | 低 | 通用语义问答 |
| BM25（关键词） | 精确好 / 语义差 | 极快 | 极低 | 型号/术语/代码检索 |
| **混合 + RRF** | **双优** | 快 | 低 | **生产默认** |
| + Rerank | 更优（精排） | 慢一点 | 中 | 精度要求高 |
| GraphRAG | 全局/多跳强 | - | **高（LLM 抽取）** | 实体关系密集场景 |

## 7. 协议与扩展机制四层对比

| 层 | 是什么 | 解决 | 类比 |
|----|--------|------|------|
| Function Calling | 模型表达调用意图的能力 | 何时调、传什么参 | 会打电话 |
| MCP | 工具接入标准（JSON-RPC） | N×M → N+M | 统一通讯录与电话系统 |
| Skills | 领域 SOP 知识包（按需加载） | 怎么做才专业 | 岗位培训手册 |
| A2A | Agent 间协作协议 | Agent↔Agent 委托 | 跨公司协作流程 |

**速记**：Skills 决定**怎么想** → MCP 决定**用什么** → Function Calling 决定**怎么调** → A2A 决定**和谁协作**。

## 8. 推理框架与部署方式

| 方案 | 吞吐 | 成本 | 运维 | 适用 |
|------|------|------|------|------|
| 闭源 API | - | 按量付费 | 零 | 起步/波动大 |
| vLLM 自托管 | **高** | 固定成本（需摊销） | 高 | 稳定大流量 |
| SGLang | 高（复杂调度强） | 同上 | 高 | 多轮/结构化输出 |
| Ollama/llama.cpp | 低 | 极低 | 低 | 本地开发/端侧 |
| 批量 API（离线） | - | **约半价** | 零 | 非实时批处理 |

**盈亏平衡直觉**：日调用稳定超过某阈值（视模型规格，通常百亿 token/月量级）→ 自托管更省；否则用 API。

## 9. 前端形态选型：低代码 vs 写代码

| 维度 | Dify/Coze 低代码 | 自研代码 |
|------|------------------|----------|
| 上线速度 | 天级 | 周级 |
| 定制深度 | 受限（复杂权限/编排难） | 无上限 |
| 长期维护 | 依赖平台版本 | 自主可控 |
| **结论** | **验证期用低代码，跑通后代码重写核心链路** | 沉淀期用代码 |

## 10. 一页决策树（打印版）

```
需求是知识问答？ → RAG（+混合检索+Rerank）
要求固定风格/格式？ → Prompt → 不够再 LoRA
要实时/私有数据？ → RAG（不要微调）
风险高（付款/删除）？ → Agent + 人工审批（HITL）
步骤能枚举？ → Workflow；不能 → Agent
任务又长又杂？ → 先单 Agent + 上下文管理，确有必要再拆多 Agent
数据敏感？ → 开源模型自部署 / Ollama
量小且波动？ → API；量大且稳定？ → vLLM 自托管
```

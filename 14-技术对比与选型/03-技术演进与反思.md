# 03 · 技术演进与反思

> 记录"哪些技术被淘汰、为什么"，比记住"现在流行什么"更能建立判断力——因为**淘汰的原因往往还在起作用**。

## 1. 技术演进时间线（按"解决什么新问题"排列）

| 时期 | 关键技术 | 解决了上一代的什么问题 | 后来被什么取代/超越 |
|------|----------|------------------------|---------------------|
| 1956-1980s | 符号主义/专家系统 | 让机器"推理" | 规则无法穷尽 → 统计学习 |
| 1990s-2010 | 统计 ML（SVM/树模型） | 数据驱动替代手工规则 | 特征工程依赖人工 → 深度学习 |
| 2012 | AlexNet/CNN | 图像特征自动提取 | 序列建模弱 → RNN/LSTM |
| 2015 | ResNet/BatchNorm | 深层网络难训练 | - |
| 2017 | **Transformer** | RNN 无法并行、长依赖差 | 至今仍是基石 |
| 2018-2020 | BERT / GPT-3 | 预训练范式 + 涌现能力 | 被 InstructGPT 等对齐版超越 |
| 2022 | RLHF/InstructGPT、ChatGPT | 让模型"好用"（对齐） | 被 DPO 简化，被推理模型超越部分场景 |
| 2023 | LoRA/QLoRA、RAG 普及 | 低成本定制 + 私有知识 | 仍是主力，未过时 |
| 2024 | 多模态统一、MoE、长上下文 | 降本增效、扩能力边界 | - |
| 2025 | **推理模型（R1/o 系）**、MCP、Agent 元年 | 复杂推理 + 工具标准化 | 演进中 |
| 2026 | Harness/Loop 工程、A2A、Skills 生态 | 从"能跑"到"可靠、自主" | 演进中 |

## 2. 被淘汰/降级的技术及其教训

| 技术 | 衰败原因 | 抽象出的教训 |
|------|----------|--------------|
| 专家系统 | 规则无法覆盖长尾，维护成本爆炸 | **穷举式方案必然败给学习式方案**（长尾是常态） |
| RNN/LSTM 做主模型 | 不能并行 → 吃不到算力红利 | **能否随算力扩展（Scalability）是生死线** |
| Word2Vec/GloVe | 静态词向量无法表达多义 | 表示能力要能随上下文动态变化 |
| 纯 Prompt 工程叙事 | 上下文动态组装才是真瓶颈 | **问题会从"怎么说"升级为"系统怎么运转"** |
| 纯向量检索 | 精确匹配/术语召回差 | 单一方法的短板会被生产场景放大 → 要混合 |
| 手工特征工程 | 表示学习自动完成 | 让机器学表示，人专注问题定义 |
| 早期 Agent 框架（重度抽象链式库） | 抽象过重、调试困难 | **抽象必须匹配问题复杂度**，过度封装是负债 |
| 传统 RPA（固定脚本） | 页面一变就崩 | 脆弱方案要被"有理解和适应能力的方案"替代 |

**共性规律（三条）**：
1. 败给**Scalability**（吃不到算力/数据红利）
2. 败给**长尾**（无法覆盖真实世界的分布）
3. 败给**脆弱性**（环境一变就失效）

## 3. 常见认知误区与反思

| 误区 | 真相 | 反思 |
|------|------|------|
| "模型越大越好" | 数据质量与后训练同等重要，7B 精调可胜 70B | 先问任务，再问模型 |
| "微调能注入知识" | 微调擅长行为而非知识，还加剧幻觉 | 知识走 RAG |
| "上下文越长越好" | 超 40% 利用率质量下滑（Smart→Dumb Zone） | 上下文是稀缺资源，要预算化 |
| "多 Agent 更强" | 4~15 倍成本，稳定性下降 | 先榨干单 Agent |
| "AI 会自己纠错" | 无验证闭环时错误会累积放大 | 独立验证机制（L5 层）不可省 |
| "Prompt 技巧是核心竞争力" | 模型变强后技巧衰减，工程与数据才是壁垒 | 别把时间全花在咒语上 |
| "benchmark 高就是好" | 榜单可污染、可过拟合 | 自建业务评测集才是真相 |
| "换个更强模型就能解决" | 大量瓶颈在配置（接口/上下文/验证） | "It's not a model problem. It's a configuration problem." |

## 4. 长期有效 vs 速朽知识（学习投资指南）

| 速朽（每季度复核） | 长期（值得深挖） |
|--------------------|------------------|
| 具体模型排名与价格 | 注意力/Transformer 原理 |
| 框架 API 细节（LangChain 版本变动） | 检索、对齐、评估的核心思想 |
| 提示词技巧清单 | 上下文/状态/验证的工程原则 |
| 榜单分数 | trade-off 分析框架 |
| 工具版本特性 | 数据质量与实验方法论 |
| 编程 Agent 某功能 | 软件工程基本功（规格、测试、抽象） |

**投资建议**：70% 时间投入长期知识，20% 跟踪速朽信息（保持手感），10% 动手验证。**判断一个知识点是否速朽的方法：问"如果模型能力翻倍，它还有效吗？"**

## 5. 学习方式反思（元认知）

1. **看会 ≠ 会讲**：能否不看资料讲 3 分钟，是唯一检验标准（所以本资料库每章都有自测检查点）
2. **输入 ≠ 输出**：写一篇笔记/做一个 demo 的价值 > 读十篇文章
3. **追新 ≠ 懂旧**：不懂 Transformer 的人追 Agent 框架，只会背概念
4. **收藏 ≠ 学习**：资料库如果只是"攒着"，就是数字垃圾场——按 [11 目录](../11-学习资源导航/README.md) 的节奏真的学下去
5. **一次搞懂 ≠ 永久记住**：需要间隔复习（用术语表随机抽检 + 面试题库自测）
